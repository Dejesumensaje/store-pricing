# Architecture & Product Decisions

A lightweight log of the decisions behind Store Pricing — so the *why* survives.

**Format (one entry per decision):**

```
### ADR-NNNN — Short title
**Status:** Accepted · **Date:** YYYY-MM-DD
**Context:** what problem / constraint prompted this.
**Decision:** what we chose.
**Consequences:** tradeoffs, what it enables, what we gave up.
```

Append a new entry per decision; don't rewrite old ones (supersede with a new ADR and link back). Newest at the bottom.

---

### ADR-0001 — HQ recommendations are proposals, not live in SAP
**Status:** Accepted · **Date:** 2026-06-22
**Context:** The grid felt "disjointed." Root cause: the code modeled HQ-pushed prices as *already live* (`applyHqReview` set `currentBasePrice = recommendedBasePrice`), so current and recommendation were the same number and couldn't be shown as distinct things.
**Decision:** An HQ recommendation is a *proposal*. `currentBasePrice` stays the live price; `recommendedBasePrice` is HQ's proposal; `newBasePrice/newRetailPrice` is the director's decision. The director decides per item: **Accept** (apply the rec), **Override** (own price), or **Keep current** (reject).
**Consequences:** The grid can show current / recommendation / decision as three real things. Margins now compute against the true current price. `hqReviewPending` means "a recommendation awaiting a decision," not "already live."

### ADR-0002 — Accepting a recommendation does not auto-send
**Status:** Accepted · **Date:** 2026-06-22
**Context:** If HQ recs aren't live, what does "Accept" do — send immediately?
**Decision:** Accept (and Override) create a *pending* change that the director then saves for later or adds to a batch and sends to SAP later. Only **Keep current** sends nothing. Rides the existing override → pending → in_batch → submitted pipeline unchanged.
**Consequences:** No new submission machinery; accept/override behave like any edit. The director controls when things go to SAP.

### ADR-0003 — Grid shows current / recommendation / decision as three price columns
**Status:** Accepted · **Date:** 2026-06-22
**Context:** Need to make "what's live, what HQ proposes, what I decided" legible at a glance.
**Decision:** Columns **Current SAP**, **HQ rec** ("—" when none), **Your price**. For temporary allowances, each shows **Base + Retail** on two lines (a TA carries two live prices).
**Consequences:** Information-rich but spatially expensive — this drove later decluttering (ADR-0005, ADR-0007). Considered but rejected: merging into one before→after column (lost the side-by-side clarity the director wanted).

### ADR-0004 — "Change type" label + short pills (TA/EDLP) with tooltip
**Status:** Accepted · **Date:** 2026-06-22
**Context:** "Pricing strategy" was ambiguous ("the current one, or the one I set?"). Long labels also crowded the column.
**Decision:** Rename the column to **Change type** (Neil's suggestion); render values as short DS Badge pills — **TA, EDLP, Base, New, Disc.** — with the full name on hover. Neutral tone (color reserved for Status).
**Consequences:** Unambiguous (a change type is inherently about the action being applied). Short pills keep the column narrow; the tooltip preserves discoverability of the full name.

### ADR-0005 — Merge Decision + Status into one column
**Status:** Accepted · **Date:** 2026-06-22
**Context:** Decision (Pending/Accepted/Overridden/…) and Status (Needs review/Edited/In batch/Pending SAP/Live) sat as two adjacent badges that overlapped (Pending≈Needs review, Changed≈Edited).
**Decision:** One **Status** column: the workflow badge is the primary signal (it's what you scan), with the HQ-relative decision (**Accepted/Overridden/Kept current**) as a quiet gray qualifier *only when it adds info*. Pending and a plain director "Changed" are left off so untouched Live rows stay calm.
**Consequences:** Removes a column and the redundancy. Decision nuance is preserved as a sub-label, not a colored badge.

### ADR-0006 — Multiple changes: badge + ⓘ tooltip, no count
**Status:** Accepted · **Date:** 2026-06-22
**Context:** A single item can change base + retail + fuel saver. We need to signal "several changes → see detail" without noise. A "3 changes" number next to the badge felt cluttered.
**Decision:** When ≥2 fields change, show a small **ⓘ** next to the status badge; hover reveals the full itemized breakdown. No count surfaced.
**Consequences:** Clean at-a-glance, detail on demand. Known tradeoff: hover detail is hidden on touch / not keyboard-reachable — fine for the desktop testing target; revisit for touch.

### ADR-0007 — Selection limited to items with a decision; no bulk editing
**Status:** Accepted · **Date:** 2026-06-22
**Context:** Users could select rows with no change, which did nothing (a dead-end). An earlier bulk-edit feature was built and then fully reverted as "wrong direction."
**Decision:** Only items with a pending decision are selectable (checkbox disabled otherwise; select-all picks only decided rows). **No bulk editing** — refine existing interactions instead of adding capabilities.
**Consequences:** The multi-select → batch flow is unambiguous. Pricing stays one-item-at-a-time via the drawer (matches how the team wants it).

### ADR-0008 — Drawer: decision up, context collapsed
**Status:** Accepted · **Date:** 2026-06-22
**Context:** The drawer stacked ~7 bordered cards; the price decision competed with margin/competitor/related/impact.
**Decision:** Cost + allowance cost move to the item header (reference info). Three explicit sections — **Base price / Retail price / Fuel saver**. Margin is inline feedback next to each price. Competitor / related / impact collapse into accordions. Labels unified to **Current SAP / HQ recommended / Your price**. Actions: Accept / Override / Keep current.
**Consequences:** The decision stays above the fold; context is one click away. Less scroll, clearer hierarchy.

### ADR-0009 — Filters: searchable accordion facets, built to scale
**Status:** Accepted · **Date:** 2026-06-22
**Context:** Flat checkbox lists don't scale to hundreds of categories/brands; active filters were invisible.
**Decision:** Rebuild `FilterDrawer` as **accordion facets** (collapsed by default, except active ones) with a **per-facet search** (appears past ~8 options), selected-first ordering, a capped list with **"Show all (N)"**, a per-facet count badge, and a **Clear** action in the facet header next to the label/pill. Use the persistent DS `Input` (not the collapsible `SearchInput`).
**Consequences:** Scales to hundreds of values per facet without virtualization. If catalogs reach thousands of *rows*, the table itself will need virtualization (still open).

### ADR-0010 — Seed a realistic catalog for filter scale
**Status:** Accepted · **Date:** 2026-06-23
**Context:** The mock had one category ("Potato chips") and ~6 brands, so the scalable filters had nothing to scale against.
**Decision:** Recategorize the hand-crafted demo items to "Snacks" (coherent) and add a deterministic synthetic catalog (~20 categories, ~70 subcategories, ~36 brands, all "Live") — without touching the demo items that drive flows (IDs, line groups, overrides, HQ recs).
**Consequences:** Filters now exercise real scale and the Category column is meaningful. `TOTAL_ITEM_COUNT` reflects the real count. Deterministic generation avoids hydration mismatches.

### ADR-0011 — Minimal default table: one adaptive Price column, granular prices opt-in
**Status:** Accepted · **Date:** 2026-06-23
**Context:** Usability review (Claire): the table showed too many columns by default — **four** price-ish columns (Change type / Current SAP / HQ rec / Your price), each stacking base+retail lines for a TA, drowned the item name. First cut over-corrected to *zero* price columns, which turned the decision queue into a phone book: Status said a decision was *owed* but gave no sense of *what's at stake* (a 2¢ nudge vs a 30% cut), so triaging hundreds of recs meant opening every drawer.
**Decision:** Default columns are **select · ID · item (pic+name) · Category · Price · Status**. The IA fix is to show the *delta*, not the *components*: a single adaptive **Price** column (`PriceMoveCell` + `priceMove()`) renders `current → target` with a ↓/↑ % move — target = the director's decision if any, else HQ's pending proposal, else just the muted current price (nothing moving). Multi-unit deals show "N for $X" with a per-unit delta; sortable by **magnitude of change** so a click surfaces the biggest movers. Direction is carried by the ↓/↑ glyph (not loaded red/green, since "good" is ambiguous between shopper savings and margin). The granular **Change type / Current SAP / HQ rec / New price** columns move into the opt-in `ColumnsMenu` (leading the list) for auditing exact numbers; "Your price" → **New price**. Store table is `flat` (no splitPane), so the column set is free to change.
**Consequences:** Clean scan *and* triage signal in one column. Mobile card drops the 3-up price triad for the same single `PriceMoveCell` line. `CurrentSapCell`/`HqRecCell`/`YourPriceCell` live on as the opt-in column cells.

### ADR-0013 — Speak the shelf: change type as a physical-tag layer, not hidden metadata
**Status:** Accepted · **Date:** 2026-06-23
**Context:** Hiding "Change type" (ADR-0011) removed the layer a director actually prioritizes on. At Hy-Vee the change type *is* a physical reality on the shelf: **base = white tag** (regular), **temporary allowance = yellow promo tag** ("SAVINGS THIS WEEK", time-bound), **EDLP = permanent reduction on the white shelf tag**, **new = a fresh tag**, **discontinued = clearance/markdown**. The push (Neil/team): don't build a *standard* table — make it look like how prices appear in the physical store, so "what am I editing / what do I prioritize" is visible.
**Decision:** Reintroduce change type as a first-class, store-grounded **Tag** column (default, replacing the old neutral "Change type" badge). `shelfTagKind()` maps each item to a `ShelfTagKind` (yellow / white / edlp / new / clearance); `SHELF_TAG_META` carries the swatch + label + price-tint. `ShelfTagCell` renders a colored tag swatch + label; the **Price target is tinted to its tag** (amber for promos, rose for clearance, emerald for new — white/EDLP stay plain) so the Price column previews the shelf and "a wall of yellow" = this week's promos. A **yellow tag also surfaces its end date** ("· ends Jun 28") since temporary allowances are the time-sensitive, prioritize-first work. New items render "Set $X" (no current → arrow). Default column order: select · ID · item · Category · **Tag** · Price · Status. Mobile card swaps its strategy Badge for `ShelfTagCell`. Direction stays the ↓/↑ glyph; tag color is the *type* lens, not a good/bad signal.
**Consequences:** The table reads like the aisle and restores prioritization by tag family (yellow promos first). Color now encodes shelf-tag *type* (semantic, store-true) while the Status badge keeps workflow state — two distinct, non-competing color systems. Open: EDLP shares the white swatch (white family) with only its label to distinguish; revisit if directors need EDLP to pop more. Grouping-by-tag (the segmented option) deferred — per-row tint covered the need without restructuring the table.

### ADR-0014 — Drawer = designing the shelf tag: live "what the shopper sees" preview
**Status:** Accepted · **Date:** 2026-06-23
**Context:** Extending the shelf metaphor (ADR-0013) from the table (the aisle seen from afar) into the drawer (the tag in your hand). The drawer was a form; a director is really deciding which tag to hang and what the customer will see. Abstract price inputs don't let them validate the decision in physical terms.
**Decision:** New `ShelfTagPreview` pinned under the item identity at the top of `ItemEditDrawer`, rendering the actual shelf tag(s) this edit produces, updating live (reads the store-driven `item`): a **white tag** (regular/permanent price, strikes "was $X" when base/EDLP changes) and, for a temporary allowance, the **yellow promo tag** — "SAVINGS THIS WEEK", the deal ("N for $X" or single), **Save** off the regular price (cents under $1, Hy-Vee style), the allowance window, and a blue **Fuel Saver** chip when active. The yellow tag dims with a dashed border + "proposed" pill when previewing HQ's rec before the director decides. New items → "New item" kicker + "Set" price; discontinued → "Clearance". Savings are computed off the **base/white-tag** price (consistent with ADR-0012's reduction reference). `shelfTagKind`/`fmtShortDate` exported from `buildStoreColumns` for reuse. Existing per-section captions ("· yellow promo tag" / "· white shelf tag") stay as the input-side anchor.
**Consequences:** The drawer now reads as "design the tag, see what the shopper sees," making the consequence of an edit tangible and validating it physically before send. Verified live (Playwright): single promo (Lay's $3.49, SAVE 80¢), multi-unit + base-change + fuel (Doritos 3/$12.00, SAVE $5.37, was $5.49, +$0.10 fuel). App-wide arc noted (batch tray = a sheet of tags to print; send = update shelf tags) but not built this round.

### ADR-0015 — White tag crossed out + drawer IA cleanup (demote the noise)
**Status:** Accepted · **Date:** 2026-06-23
**Context:** Neil's shelf photo shows the white tag **X'd out** when a yellow promo is the active price. And an IA review of the drawer found redundancy/noise competing with the decision: the proposed price `$2.50` appeared 3× (preview, reference grid, accept button); a titled, non-actionable locked "Price type" block; a generic HQ note ("accept it, enter your own, or keep") that the accept-first buttons already imply; and inline margin rows (analyst detail). Sarah: the director should *understand what's being recommended*, not just see a price.
**Decision:** (1) **White tag gets a red X** in `ShelfTagPreview` when a yellow promo is present (`crossed` prop, SVG diagonal). (2) Four IA demotions in `ItemEditDrawer`, all confirmed by the user: **remove the per-section price reference grids** (Current SAP / HQ rec) in both retail + base — the shelf preview already shows crossed white + yellow; **collapse the locked "Price type" block to a one-line caption** ("🔒 Temporary allowance · price & dates editable, type set by HQ"); **replace the generic HQ note with the rationale** (`hqRecRationale()` → "HQ proposes a vendor-funded promo · save 69¢ · runs Jun 24–30" for TA, "HQ recommends lowering the price to $X (from $Y)" otherwise); **move margin rows into the "Projected impact" accordion** (consolidated financials). (3) Seeded a clean TA **proposal** in the HQ queue (mock `RBCS5-9` Goldfish, added to `HQ_REVIEW_IDS`) to exercise the accept-first "what HQ recommends" flow + the "proposed" preview state.
**Consequences:** The drawer is dramatically calmer — decision (Accept $X / Set a different price) up top, the shelf preview carries the prices, context explains the *why*. `$2.50` now appears 2× doing two different jobs (result vs action) instead of 3×. Verified live (Playwright) on the HQ proposal (Goldfish) and an edit-mode TA (Doritos).

### ADR-0016 — "Tags to hang": the send flow as a pile you build and clear (kill the teleport)
**Status:** Accepted · **Date:** 2026-06-23
**Context:** Usability test on batch sending surfaced three things: (1) people love the *feeling of clearing/resolving* — the empty HQ tab felt like "mission accomplished"; (2) the "To send" screen was badly disconnected — Sarah circled, never found the batches, repeatedly tried to reach them *from the drawer*; (3) the root cause: the mental model is "I'm editing things," but swapping context to a separate batch screen made the edits *disappear* — they couldn't find where their changes went. Extending the shelf metaphor: editing = **printing a tag**; the edited items = a **pile of tags to hang**; sending = **hanging them on the shelf**; the empty pile = the satisfying release.
**Decision:** Replace the full-screen `view="batch"` teleport (primary path) with an **in-context sheet** (`TagsToHangSheet`, a DS Drawer that slides *over* the items table — same context). The "To send" button → **"Tags to hang"** (icon `Tags`), always visible with a live count, so edits never feel lost. The sheet lists the pending pile as **tag-styled rows** (shelf-tag swatch, Base/Retail, current → tinted new price), **yellow promos first**, each removable. Primary action **"Hang all N on the shelf"** → `sendAllPending` → success toast + the sheet flips to a **celebration empty state** ("Shelf's all caught up · every tag you printed is hung"). An "Or organize into batches to schedule" link still opens the full `BatchTrayView` (advanced; not dead). **Drawer footer reworked**: removed the confusing in-drawer batch assignment (`BatchSplitButton` / "Add to batch" — what Sarah fought) in favor of a clear pile connection — **"🏷 In Tags to hang · Review"** (new `onReviewTags` prop closes the drawer + opens the sheet) next to Next item / Done. Dropped the drawer's `activeBatch`/`openBatches`/`onAddToBatch`/`onNewBatch` props.
**Consequences:** Edits accumulate in a visible pile, reviewed in-context, cleared with a satisfying "done" — the three findings addressed in one move. Named batches/scheduling survive as an opt-in advanced path, not the default. Verified live (Playwright): pile sheet over the table (5 tags), hang-all → "5 tags hung" toast + celebration, drawer footer "In Tags to hang · Review". `SHELF_TAG_META` exported for the sheet's swatches. The bulk ActionBar still uses the batch helpers (unchanged). **Superseded in part by ADR-0017** (the separate sheet became a lens on All items).

### ADR-0017 — One home: the tag lifecycle; "Tags to hang" is a lens on All items, not a destination
**Status:** Accepted · **Date:** 2026-06-23
**Context:** Holistic rethink after more feedback. Consistency problems: three competing concepts (HQ queue, the Tags-to-hang pile, batches) and two surfaces deciding "what happens to my edit" (drawer + separate page). User's framing: the mental model is "I'm editing"; a separate destination makes edits *disappear*. Also: the HQ tab must drain and **stay empty** after sending (decided items live in All items); recently-touched items should rise to the top of All items. The metaphor gives a clean lifecycle.
**Decision:** One lifecycle, **one home (All items = the shelf)**: **Needs review** (HQ proposal) → **Ready to hang** (decided/"printed") → **Hanging** (sent) → **Live** (confirmed); `in_batch` = **In a tag run** (`item-status.ts` relabeled, tones kept). **"Tags to hang" is now a LENS over All items**, not a separate sheet: the header button toggles `hangLensOn`, which filters the same table to the ready tags and shows a **Hang-all bar** ("N tags are printed and ready · Hang all N on the shelf") + a "Schedule a tag run instead" link (→ the advanced batch workspace); clearing flips to the in-place celebration ("Shelf's all caught up"). `TagsToHangSheet` retired as the destination. **Recent-first**: added `Override.updatedAt` (set in `upsertOverride`); All items sorts items with active edits to the top, newest first. The button count + lens + bar all use the **item** count (`pendingItemIds.size`), not the override count, for consistency. Drawer footer connection relabeled to **"Ready to hang · View tags"** (`onReviewTags` now opens the lens). Decisions confirmed with the user: lens-over-All-items (vs. separate sheet), and HQ accept routing kept **optional & inline**.
**Consequences:** One surface, one mental model — edits never teleport; the director sees their work in the shelf they already know, recent on top, and clears it in place. HQ already drains permanently (`hqReviewNeeded` excludes decided items); decided items now surface recent-first in All items. Verified live (Playwright): All items lifecycle statuses, lens filter + Hang-all (4 items) → "4 tags hung" + in-place celebration. **Superseded in part by ADR-0018** (HQ tab → guided flow).

### ADR-0018 — HQ review is a guided flow, not a tab; All items is the recommendation-free home
**Status:** Accepted · **Date:** 2026-06-23
**Context:** Simulating the whole journey (screenshots) exposed real incoherence — the build had been patched, not designed. Concretely: the HQ banner still said "HQ set these prices and they're **already live**" (contradicting the proposal/accept/hang model); **two** "Accept" buttons (inline + footer); the drawer titled "Edit prices" while *reviewing*; accepting didn't auto-advance (no drain); the journey was fragmented across four disconnected surfaces (All tab, HQ tab, Tags-to-hang lens, batch view). Root IA error: the pipeline stages (Proposal → Decide → Ready → Hung) were presented as peer tabs, not one flow.
**Decision:** Two real things, not four. **All items = the shelf**: the director's permanent, *recommendation-free* workspace to find any item, see its live state, and edit prices on their own terms (ad-hoc edits → "Ready to hang" → hang via the lens). The **MainTabs (All/HQ) are removed**; All items is just the home, titled with its count. **HQ proposals are a guided flow** (`ReviewFlow`, new): a focused, one-proposal-at-a-time experience (`reviewMode` swaps the main content) — shelf preview + rationale + **Skip / Tweak / Accept**, each **auto-advancing**, with a progress bar and running "N ready to hang" tally; at the end, a summary → **"Hang all N on the shelf"** → toast + celebration. One continuous motion: review → decide → drain → hang. Entered from a clear CTA on All items ("HQ sent N recommendations to review — Review →", pulsing dot) and the header bell. The stale "already live" `HqReviewBanner` is gone; `hqRecRationale` extracted to `src/lib/hq-rec.ts` (shared by the drawer + ReviewFlow); `TagsToHangSheet` deleted (superseded by the lens). `activeTab`/`MainTab` removed; drawer `flow` fixed to "all".
**Consequences:** The two top jobs are now coherent and separate: **"review what HQ sent"** and **"manage my prices"** (All items, no recs in the way). **Review interaction refined in ADR-0019** (the 1-by-1 wizard → a scannable worklist).

### ADR-0019 — Review is a scannable worklist (bulk + dive-in), not a 1-by-1 wizard; HQ stays drained after send
**Status:** Accepted · **Date:** 2026-06-23
**Context:** The guided 1-by-1 card (ADR-0018) felt good but was **too extreme**: HQ can send ~100 recs, and a forced linear march is exhausting and **strips decision context** (you can't see neighbors, patterns, or decide in bulk). Also surfaced a real bug the user predicted: after **hanging** (send → override goes `submitted`), `hqReviewNeeded`'s `!hasOverride` flipped back true and accepted recs **re-appeared in the queue**.
**Decision:** `ReviewFlow` rebuilt as a **worklist**: all recs in a scannable list (context + patterns), each row = item + rationale + `current → proposed` (tinted to its tag) + %/flag, with inline **Accept ✓ / Skip ✕ / open ›**. **Bulk**: select-many → "Accept selected (N)" + "Accept all N". **Sort**: Needs attention (flagged — alerts or ≥15% swing — first, then magnitude) / Tag / Item. **Dive-in** (`onOpenItem` → the drawer) gives the full card only for the ones that need a closer look; the 1-by-1 focus is now opt-in, not forced. The list **drains live** (rows leave as decided) → ends in the same summary → "Hang all N" → celebration. **Bug fix**: deciding on an HQ rec (accept/override via `updateBasePrice`/`updateRetailPrice`) now sets `reviewed: true`, so it leaves the queue *permanently* and never returns after the override goes submitted. Seeded 8 extra HQ proposals (`HQ-101…108`, mix of routine + flagged) so the worklist shows real scale.
**Consequences:** Review now scales (bulk-accept the routine, dive into the flagged few) while keeping context, and still delivers the drain→send payoff. After send, HQ stays empty; decided items show their state in All items. Verified live (Playwright). **Metaphor copy + batch model reworked in ADR-0021.**

### ADR-0021 — Dial back the metaphor copy; batches = inline scheduled sends (no workshop)
**Status:** Accepted · **Date:** 2026-06-23
**Context:** Two honest user notes: (1) the shelf metaphor was **over-applied to workflow copy** ("Tags to hang / hang on the shelf / printed / tag run") — cute, not clear; (2) **batches still felt clunky** — a heavyweight parallel system (separate `BatchTrayView` workspace + `NewBatchModal`), and the "include in a batch?" decision was disconnected from where it makes sense.
**Decision:** **(a) Language dial-back** — the metaphor stays where it's *real* (the drawer's white/yellow "what the shopper sees" tag preview, base=white tag / retail=yellow tag), but the workflow speaks plainly: **"Tags to hang" → "To send"**, **"Hang all on the shelf" → "Send all to SAP"**, **"printed/ready to hang" → "ready to send"**; statuses **Ready / Sending / Scheduled / Live** (`item-status.ts`); celebration "All caught up / All sent". **(b) Batch = a scheduled send, inline** — there is no separate workshop or create-batch modal in the primary flow. On the **To send** surface you either **Send all to SAP** now, or **select rows → Schedule… → pick a date** (small Modal + `DateField`) which groups them into a **scheduled batch** shown inline ("Scheduled · Jun 24 · 3 items · Send now"). The per-item "batch or not" decision is gone — you approve into "To send", then group/schedule there with full context. Implemented in `page.tsx`: `sendSelectedNow` (createBatch+submitBatch), `scheduleSelected` (createBatch+scheduleBatch), the ActionBar now offers **Send now / Schedule…**, and a Scheduled section lists scheduled groups. Removed the `BatchSplitButton` from the bulk bar + the dead `addOverridesToBatch`/`handleBulkAddToBatch`. Counts standardized to **items** (not override records) across the surface.
**Consequences:** Clearer copy; batching is now a lightweight, contextual action instead of a parallel system. **Batch model corrected/expanded in ADR-0022** (batches are central, not an afterthought).

### ADR-0022 — Batches are the central object: an "Unassigned" inbox you sort into multiple scheduled batches
**Status:** Accepted · **Date:** 2026-06-23
**Context:** Key domain correction from the user: in their real system **batches are a central control mechanism**, not an optional scheduled send. A store runs **multiple active batches concurrently, each scheduled independently** — because sending *all* a store's changes to SAP at once would overload printing/control. So the director has **two conscious decisions**: (a) the price (accept/edit), and (b) **which batch + when** (throughput management). ADR-0021 under-modeled (b) as a hidden afterthought. Batches must be **evident and central**, and assignment must be a deliberate, scalable act — drawer included.
**Decision:** The **To send** surface is now batch-centric, pattern = **Unassigned inbox + a list of your batches** (the chosen IA pattern over kanban / batch-builder). **"Your batches"** (the control panel) lists every draft/scheduled batch with name, status (Draft/Scheduled), schedule date, item count, and per-batch **Schedule** (Modal+`DateField` → `scheduleBatch`) / **Send now** (`submitBatch`) / open-to-**manage** (`BatchDetailDrawer`), plus **+ New batch** (`NewBatchModal`). **"Unassigned (N)"** is the inbox of changes not yet in a batch (pending overrides); select rows → **Add to batch ▾** (`BatchSplitButton`: existing batch or new) — they move into the batch (in_batch → leave Unassigned, batch count grows), Undoable. A de-emphasized "Send all now / Send now" remains for the odd urgent change (batches are the controlled default). **Per-item assignment is back in the drawer footer** ("Add to batch ▾" via `BatchSplitButton`, restored `openBatches`/`activeBatch`/`onAddToBatch`/`onNewBatch` props) so the batch decision is available both in bulk and per-item. Shared `addOverridesToBatch(batchId, ids)` powers both. Mock seeds two concurrent batches (Tuesday ad prep / Friday endcap reset) to show the multi-batch reality.
**Consequences:** Batches are now the evident, central organizing structure with independent schedules — matching how throughput is actually controlled. Verified live (Playwright): To-send shows 2 batches + Unassigned; select 2 → "Add to Friday endcap reset" → batch 1→4 items, Unassigned shrinks, Undo toast; per-batch "Schedule this batch" modal; drawer footer "Add to batch ▾". Open/next: the old `BatchTrayView` workshop (`view==="batch"`) is fully superseded and **orphaned/unreachable** — delete in a cleanup pass; no sent/confirmed batch *history* view yet (items show Sending/Live in All items). **Review→batch handoff fixed in ADR-0023.**

### ADR-0023 — Connect Review → To send → batches (the handoff seam)
**Status:** Accepted · **Date:** 2026-06-23
**Context:** The Review worklist was disconnected from the batch model. Accepting said "ready to send" but gave **no option to add to a batch**, **no indication the changes fed the To-send queue**, and its end-action **"Send all to SAP" bypassed batches entirely** (you'd send without ever seeing your other batches — the anti-pattern). Plus the success toast (top-right) **covered the "To send" button**.
**Decision:** Make Review *feed* the batch workflow instead of routing around it. **(1)** Removed the review's "Send all to SAP" end-action; the summary now reads "N changes are now in To send. Sort them into batches…" with a primary **"Go to To send"** (`onGoToSend` → exits review, opens the To-send surface where batches live) + "Back to all items". **(2)** Evidence it feeds the queue: a header **"✓ N in To send"** chip (links to To send) + the accept toast "Added to To send" + the live header "To send (N)" count. **(3)** The batch option *during* review: the bulk bar gained **"Add to batch ▾"** (`BatchSplitButton`) — `acceptSelectedToBatch` accepts the selected recs AND drops their overrides into a batch in one step (for directors who sort as they review). `ReviewFlow` gained props `onGoToSend`/`openBatches`/`activeBatch`/`onAddToBatch`/`onNewBatch`; dropped its own `sendAllPending`/hung/celebration. **(4)** Moved `ToastProvider` to **bottom-left** so toasts never cover the To-send button (top-right) or the bulk ActionBar (bottom-center).
**Consequences:** The pipeline is now continuous — Review decides prices → changes land in To send (visibly) → you sort into batches there (or during review). No send that skips the batch view. Verified live (Playwright): bulk "Add to batch" in review, "N in To send" header chip, end "Go to To send", toast at bottom-left clear of the button.

### ADR-0012 — Temporary-allowance drawer: accept-first, pick-the-discount-kind-first, optional base
**Status:** Accepted · **Date:** 2026-06-23
**Context:** Usability test (Sarah + Neil/HQ). Every retail-price input (% off, $ off, exact, multi-unit deal) was visible at once, so the decision wasn't conscious. Mental model clarified: **base price = white shelf tag** (regular), **retail price = yellow tag** (the promo). Sarah wanted to lean toward accepting the recommendation with the option to change — not all options up front. Percent-off was computed off current retail and read as confusing; it should be off the **base** price ($4.49 × 0.9 ≈ $4.04).
**Decision:** In the TA drawer the **retail (yellow-tag) decision is primary** and **accept-first**: when HQ has a rec it opens on `Accept $X.XX` + `Set a different price`. Choosing to change reveals a single **reduction-method chooser** — `% off · $ off · Multi-unit · Exact price` (kind first, number last) — mounting **one input at a time** (`RetailReductionField`). `% / $ off` now reference the **base/white-tag** price with inline math ("10% off $4.49 (base) = $4.04"). The **base price section is optional** in TA (a Switch like fuel saver), default collapsed. Captions name the tags ("yellow promo tag" / "white shelf tag"); the recommendation renders **grayed** as a suggestion. Labels: **New base price / New retail price** (was "Your price").
**Consequences:** Progressive disclosure makes the discount type a conscious choice. `ReductionInput` gained a controlled `mode`/`hideToggle` so the chooser owns $/%. Known tradeoff: switching method after committing can briefly re-shape an existing deal (e.g. exact→multi); fine for the test. Batches flow intentionally untouched this round.

### ADR-0024 — Polish pass: To-send reachable from review, no drawer item-hopping, louder send feedback, batch landing flash
**Status:** Accepted · **Date:** 2026-06-23
**Context:** Four UX refinements from the user after living with the ADR-0023 pipeline. (1) The "To send" button shows during HQ review but clicking it only toggled the `hangLensOn` lens *under* the still-active `reviewMode`, so nothing happened — you couldn't jump to To send mid-review. (2) The drawer's prev/next item navigation (header `‹ X / Y ›` + footer "Next item") made the editing flow feel like a forced march; the user wanted to just finish an item and close back to the underlying flow, in both All items and HQ review. (3) The "To send" count increment was easy to miss (only a small badge pop). (4) Adding items to a batch on the To-send surface gave a toast but no spatial cue of *where* the items landed.
**Decision:** (1) The To-send button's `onClick` now special-cases review: `if (reviewMode) { setReviewMode(false); setHangLensOn(true) }` → exits review and opens the batch-centric To-send surface. (2) **Removed the drawer's item-to-item navigation** entirely — dropped the `onPrev`/`onNext`/`position` props, the header `‹ X / Y ›` control, and the "Next/Next item" footer label; `advance()` is now just `onClose()`, footer reads **"Done"**. Page no longer computes `rowIds`/`drawerIdx`/`onPrev`/`onNext`. Finishing an edit closes the drawer and returns to All items or the review worklist. (3) **Louder increment feedback**: enhanced the `badge-pop` keyframe (bigger overshoot + settle) and added a `send-bump` keyframe that bounces the *whole* To-send button (re-keyed by the existing `trayPulse` counter). (4) **Batch landing flash**: new `batch-flash` keyframe (brand-tinted bg + ring fading out over 1.5s); `addOverridesToBatch` and new-batch creation set `batchFlash {id, n}`, and the matching batch row re-keys while flashing so the highlight restarts even when the same batch is targeted twice. Also gave the review worklist's per-row **Accept/Skip** a clearer hover (Accept scales up; Skip scales + turns red to telegraph "reject"). All animations honor `prefers-reduced-motion`.
**Consequences:** Review → To send is reachable in one click; the drawer is a focused single-item editor (no hopping); increments and batch assignments are visually obvious. Verified live (Playwright): To-send from review leaves review and shows "Your batches"; drawer has 0 nav controls + a single "Done"; adding to a batch flashes its row (brand ring + tint) with the Undo toast. `tsc` clean; eslint at pre-existing baseline (set-state-in-effect / no-unused-expressions only).
